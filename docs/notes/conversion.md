# Conversion notes: marker, vision, translation, text repair

Gotchas learned while converting PDFs to markdown. Read alongside the "Conversion failure modes" table in the repo `CLAUDE.md`, which this file does not repeat.

## Before converting: probe the PDF

### Classify a PDF by its pages, not its filename
`mmc2.pdf` (Elsevier's name for a supplementary file) was the whole of `o'connor2025z`: cover with graphical abstract on p. 1, article from p. 2, supplement from p. 10. It was misread as "supplement only" from the filename plus the first 220 characters of four pages. Before calling a file a supplement, a cover or a wrong paper, find where each part starts (`Introduction`, `Supplemental`, `References`) on every page.

### Probe the text layer before running marker on any pre-2000 scan
Marker with `--disable_ocr` passes through whatever embedded OCR the PDF has, and substitution garbage ("lhe lin;[ aJeguately known", "L'niver~ity", "Trrassic") evades `intake_qc.py` (high B/page), `scan_markdown_quality.py` (ASCII, not PUA) and the language audit (still English-ish). A clean title line does not mean a clean body. hopson1975a (Sabinet scan) passed at 5,772 B/page fully garbled.
`/intake`'s path hint uses year ≥ 1900 → Path A, which is wrong for post-1900 letterpress scans: `gilmore1946b` (USGS 1946) hinted A but its text layer read `CHARLES W. GILMOEE`, `SHOETEE CONTEIBUTIONS`. For any scanned reprint, pre-2000 paper, or "Reproduced by ... Gateway" watermark, run the text-layer probe from CLAUDE.md first; if garbled, `scripts/intake_acquire.py KEY --vision-ocr "<reason>"` directly. After marker, read a real prose paragraph (`sed -n '5,15p'`) before declaring ok.

### Front-loaded text layer: probe a middle page, and read the tail on a stub flag
A non-zero text layer does not mean marker will work. `hunt1992a`: 2,487 chars, all from the NMGS download cover; body image-only, marker output 96 B/page. `buffetaut1986b`: 2,852 chars on page 1 only; marker stopped mid-sentence and lost Table I.
Print a per-page character count (pypdfium2 loop over `get_text_bounded()`) rather than a total. When `intake_qc.py` flags `likely_stub`, run `tail -c 300 markdown/KEY.md`: the head is the part with a text layer, so it always looks fine; truncation shows at the tail (a sentence ending in a colon).

### 1900-1919 papers: decide by text-layer quality, not year
BAMNH, RSC Transactions, Comptes Rendus and JSTOR-scanned plate-heavy monographs of this era usually need vision: small-caps misreads (`BarRnuM Brown`, `Pirate XLII` for Plate XLII, `Wdmonton`, `LawrencE`), rotated plate captions extracted as CID garbage, and plate-diluted B/page that trips `likely_stub`. Pre-flag them with `intake_acquire.py --vision-ocr` (precedents `brown1914b`, `brown1914c`, `lambe1919a`).
US Government Printing Office products of the same era (USGS, Smithsonian) often have clean text layers: `gilmore1917a` (USGS PP 103) ran marker with ~0% prose garble; vision would have wasted ~$2.70.
Probe interior pages, not page 1 (title pages misread even in clean scans). This refines the intake skill's "1900-1919 -> Path A first" rule.

### Stub markdown: wrong PDF or image-only body?
A 1-3 KB stub has two causes with different fixes. Wrong PDF (splash/landing page from a fetcher): small file, page count far below the article length — replace the PDF; vision would OCR the splash page perfectly. Real PDF with image-only body: plausible page count, ~150-300 B/page, cover boilerplate ("This article was downloaded by", "Informa Ltd") — set `vision_ocr_needed`. Both can occur in one batch (after replacing 6 wrong PDFs, zhao1999a, charig1986a, sampson1995a were still image-only T&F scans). Check PDF size and page count against the citation before choosing.

### A partial PDF passes every QC gate; check the section flow
`ibiricu2014a` (Notohypsilophodon reappraisal, Zootaxa 3786.4) was a 6-page "first pages + references" excerpt: title → abstract → introduction → one figure caption → acknowledgments → ~110 references, with no Systematic Paleontology, diagnosis or holotype (UNPSJB-PV 942). B/page, the image-only probe and the language audit all passed. For any taxonomic description paper, `grep -iE 'systematic|diagnosis|holotype|description|referred' markdown/{key}.md`; zero hits on a paper whose abstract describes a taxon means re-source the full PDF. A short page count for the journal is a secondary sign. Log it in `corpus-paper-report.md`.

### Scope-limited vision OCR for whole-volume PDFs
When the PDF is a whole volume but the cited article is a few pages, do not run `scripts/convert_with_vision.py` on the full file (it has no page limit; e.g. hitchcock1865a is 104 pp for a 2-page appendix). Run an inline one-shot that mirrors its prompt (`PROMPT_VERBATIM`) and cache layout (`.runtime/cache/vision/{key}/page-NNNN.json`, pages joined with `\n\n---\n\n`), on only the target pages; set `tool=claude-vision`, note the scope in `conversion.notes`, and leave the PDF intact. Cited page ≠ PDF page: `marsh1885a` cited p.169 = PDF p.1; `hitchcock1865a` cited pp.39-40 = PDF pp.48-49. Ask the user for the physical pages.

### Compressing oversized scans: details beyond CLAUDE.md
`scripts/compress_pdf.py KEY` re-renders pages to JPEG and steps `max_dim` down until under `--target-mb` (default 90, the LFS soft cap). Always pass `--keep-source` with a path outside the repository (e.g. `--keep-source ../{key}-full.pdf`), because the source is uncommitted at intake.
500+ page volumes can bottom out above the cap (`jones2026c`, 520 pp, stuck at 98.2 MB): the loop now drops JPEG quality to a ~58 floor after the dimension floor. If a run still fails, restore the source backup before re-running; never re-compress an already-compressed output.
Resolution loss costs vision OCR nothing as long as the long edge stays near 1568 px, because `convert_with_vision.py` caps pages there anyway.
Order: compress, then `intake_acquire.py`, then convert. `intake_acquire.py` rebuilds the acquisition block and drops any `pdf_compression` annotation, so record the compression in the commit message.
Any key that went through compression has no text layer (precedent `sotoacuna2024`, 134 MB to 17 MB, 0 text chars afterwards): route it to vision, not marker, regardless of year.

### Image-heavy text-layer PDFs: downsample in place, marker the text-identical copy
Two failure-prone routes for an oversized PDF that HAS a good text layer (`suarez-gonzalez2015b`, a 412-page thesis, 689 MB, 679 MB of it in 192 images at up to ~1100 dpi spread over 111 pages, so "split out the few big figures" does not apply):
- `compress_pdf.py` re-renders pages and destroys the text layer.
- Ghostscript `pdfwrite` with image downsampling (200 dpi, 54 MB) keeps a text layer but breaks the "Th" ligature on 45 pages ("The" -> "Te", "Thrombolites" -> "Trombolites"). Bag-of-words compare before trusting it; a raw string diff hides this behind harmless `fi` -> `ﬁ` changes.
PyMuPDF `Document.rewrite_images(dpi_threshold=210, dpi_target=200, quality=82)` then `save(garbage=3, deflate=True)` leaves every page's `get_text()` byte-identical (152 MB here; some images nested in form XObjects are skipped). Run marker on that copy, commit the Ghostscript copy for viewing, and say in `acquisition.note` that the committed PDF's own text layer has the ligature fault.

### Marker memory on 16 GB: use --low-memory, and kill the workers, not just the parent
Default batch sizes took a marker worker to ~20 GB RSS on a 512-page thesis and thrashed swap (12 minutes without finishing an 18-page paper queued with it); Claude Code then reaped the background job. `convert_with_marker.py --low-memory` passes small layout/detection/recognition/table batch sizes and `--highres_image_dpi 120`; an 18-page paper then ran in 2.1 min with the worker at ~6-8 GB. Convert big PDFs one key per run.
`pkill -f convert_with_marker.py` and `pkill -f bin/marker` do NOT stop marker's workers: they run as `Python -c from multiprocessing...` and get reparented to PID 1, holding their memory (one held 19 GB after its parent was killed). Find them with `top -o mem` or `ps -axo pid,ppid,etime,command | grep multiprocessing` and kill them by PID. Happened again 2026-10-14: a 10-PDF batch run without `--low-memory`, containing `gregory1931a` (USGS PP 164, 196 pp. with fold-out plates embedded at up to 7953 × 5418 px) and `dowling1917a` (216 pp.), took the worker to 23 GB and the user noticed the machine slow down. Before any batch, check for a PDF over ~100 pages or an embedded image over ~20 MP (`fitz` `page.get_images(full=True)` gives pixel sizes); if there is one, use `--low-memory` for the whole batch and give the big PDF its own run. `ps -o rss` showed 0 for the worker here; `top -l 1 -o mem` showed the real figure.
Later the same day, `--low-memory` was not enough either, and the cause was not big pages. Born-digital `fang2016z` (56 pp., an Elsevier accepted manuscript with nothing over 2 MP) and `ning2024z` (69-page bioRxiv preprint) each took the worker past 10 GB within ~25 s, run alone. The preprint did so even as a 307 KB copy with every image deleted. Both had many tables; four smaller papers in the same batch converted fine. A 9 GB watchdog stopped each run; both went to vision ($1.31 for 125 pages, recall vs the text layer 1.0 for fang; the preprint's only gap was its per-page bioRxiv licence stamp). `TORCH_DEVICE=cpu` (see below) was not tried. Two process lessons: (1) `convert_with_marker.py` copies outputs into `markdown/` only when the whole batch ends, so killing the batch for one bad PDF throws away every paper it had finished. When a batch might be stopped, run one key per process. (2) Being third in the batch twice looked like memory building up across documents, but it wasn't: the same PDF failed again on its own.

### PDF compression does not reduce vision tokens; DPI does
Image tokens depend on rendered pixel dimensions (≈ w×h/750), and `scripts/convert_with_vision.py` renders at a fixed `--dpi`. At 150 dpi carroll1977a (0.4 MB) cost 2,671 tokens/page and soares2020a (25.5 MB) 2,697. Compression only blurs the image and, via `compress_pdf.py`, destroys the text layer. 150 dpi ≈ 2,800 tokens/page, 120 ≈ 1,795 (−36%), 100 ≈ 1,247 (−55%). Keep 150 as default (specimen numbers and diacritics are small text); use `--dpi 120` for plain-prose bulk jobs.

### Local Surya OCR is not a cheaper middle tier
Measured on `carroll1977a` (4-page scan): marker without OCR ~7 s/page; marker `--ocr` (Surya) >45 s/page and killed; Sonnet vision ~9 s/page at concurrency 3. The saving (~$0.018/page) is not worth >36 h compute on the backlog, and Surya is worse on old letterpress. Tesseract is lower quality still. The cost levers are DPI and which pages are sent.

## Marker failure modes

### Marker can drop a BHL partpdf article page and keep only the attribution page
BHL partpdf exports are article page(s) plus a trailing BHL attribution page. When the article pages have a word-broken text layer (one word per line, common in BZN), marker can drop them and keep only the boilerplate. iczn1995a (ICZN Opinion 1801): 483 B/page, body was pure attribution; page 1 held 2,664 chars per pypdfium2. `intake_qc.py` flags it `likely_stub`. Diagnose by comparing markdown against per-page pypdfium2 text; fix with `vision_ocr_needed=True` + `scripts/convert_with_vision.py` (0.9 KB → 3.4 KB, $0.03).

### Marker can drop the title of an accepted manuscript
On `mcphee2016b` (Cretaceous Research accepted manuscript) the title sat directly under a bare page number and marker treated it as a running head; the markdown began at the author line. Every QC gate passed (`intake_qc` ok at 2,575 B/page). For a stub-orphan with a blank manifest citation, the markdown title is the only text identifying the paper. After marker on any AM/preprint layout, compare `head -c 200 markdown/{key}.md` with page 1 of the text layer. If missing, prepend the title as an H1 copied verbatim from the text layer; re-running marker gives the same result.

### Marker MPS out-of-memory usually means one oversized foldout page
`RuntimeError: MPS backend out of memory ... Tried to allocate 2.72 GiB` in surya's layout encoder is caused by a single oversized page (the layout model still runs under `--disable_ocr`), not cumulative memory. Tell: same allocation numbers when the key is re-run alone. Probe page sizes (`d[i].get_width()/get_height()` for every page) and look for outliers. `lull1942a`: 272 pages at ~445×693 pt, foldouts at 1876×698 and 1205×698.
Fix: `TORCH_DEVICE=cpu ./.runtime/venv/bin/python scripts/convert_with_marker.py --workers 1 --force --key {key}` (272 pages in 8 min). If the OS kills the CPU run for memory (`stoyanow1949a`, a plate at 6.6× median page area), copy the full PDF to scratch, `scripts/extract_pdf_pages.py {key} "<ranges without foldouts>" --no-manifest`, convert, then restore the full PDF; record the exclusion in `conversion.notes` and set `page_count` to the converted count. Foldouts are often the correlation chart or locality map, so offer to vision-OCR just those pages afterwards. Do not set `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0`.

### Marker reference links swallow the end of the preceding word
Marker opens superscript reference-call links too early: `Zhiluo Formatio[n50,](#page-13-20)`, `Guangdong Provinc[e18.](#page-13-8)`, `Carballido et al[.2](#page-10-0)`. The word becomes unsearchable. 2,266 sites over 127 files were repaired 2026-09-16 by `scripts/repair_marker_ref_links.py` (verified against the PDF text layer, which keeps word and call fused as `Province18.`). Run `scripts/fix_dropped_ligatures.py` first, since some proposals fail on `ossifcatio`-type words. The author-affiliation form (`Oter[oa]`) is ambiguous and sits behind `--affiliations`, off by default.
Two worse defects are not auto-repairable and need a human reading the page: brackets interleaved through a word (`arya](#page-72-0)n[ska, 1977]` = "Maryanska, 1977"; 209 sites) and prose swallowed into link text (`the follo[wing combination o](#page-6-0)`; 130 sites). `--audit` counts both.

### Hundreds of single-letter `<sup>X</sup>` tags mean a broken text layer
Chinese DTP pipelines set Latin text in SimSun fullwidth glyphs and flag every glyph as superscript; marker wraps each letter in `<sup>`. `dong2001` (CSVP proceedings) had 10,255 single-letter tags and degraded spacing underneath. Count with `re.compile(r"<sup>[A-Za-z]</sup>")`:
- over 1000 → vision re-OCR (`intake_acquire.py --vision-ocr` + `convert_with_vision.py --key`).
- 30–500 → sporadic font hiccups with correct text underneath; strip `<sup>([A-Za-z])</sup>` → `\1` (digits and multi-char superscripts are untouched).
If the letters under `<sup>` follow English frequency (e t a o i n...), it is full-body pollution.

### Marker can blow one table up into a block of duplicated cells
On `bordy2004z` a ~3 KB table became 123 KB (68% of the file): 46 rows, every row exactly 2,676 chars, one column replicated into every row with `<br>`. It passes every QC gate (the file is large, not small). Detect with the largest paragraph and its line lengths:
`paras=[p for p in md.split('\n\n') if p.strip()]; big=max(paras,key=len); print(len(big), len(big)/len(md), {len(l) for l in big.split('\n')})`. Identical row lengths are conclusive. Fix by vision re-OCR of the whole key, not by splicing a repaired table into marker output (that leaves `conversion.tool` wrong).
The padding variant (sohl1960a, saitta2026a: 99% whitespace, nothing lost) is handled by `scripts/compact_padded_tables.py`. Check the real-character share first. A table that has swallowed prose (two-column page beside a measured section) loses reading order; splice a vision read of that page.

### Marker can keep the tables of a bilingual Chinese paper and drop all the Chinese prose
When the Chinese body font has a broken CID map, marker skips those runs while Latin/numeric tables survive. hu2016a (Beipiaognathus, Journal of Geology 40): 6 pages, 402 B/page, tables only; vision gave 2,806 B/page. Signs: `likely_stub` at 300–800 B/page, body opens with a table, zero CJK characters, Chinese publisher (DOI 10.3969/j.issn...). There is nothing to translate; route to vision OCR.

### Gutter-numbered accepted manuscripts: marker deletes whole lines
Beyond tabling text (fixed by `untable_gutter_manuscript.py`), marker runs paragraphs together, hoists headings above their first lines, and deletes whole lines: 15 of 457 in `longrich2024c` (five reference entries, a table row, seven caption lines). All QC passes, and word counts can exceed the source because surviving tables inflate the file.
Tell: a gap in heading numbering. Measure against the born-digital text layer: strip the page number and the leading gutter number from each line, fingerprint the middle six words, look for it in the markdown. Delete markdown `*` rather than replacing with a space; verify by hand lines where a gutter number is glued mid-word (`three187`).
Fix: vision re-OCR with `--extra-context` naming the gutter, `--pages` to skip back plates.
Manuscript-style supplements have the same gutter, so check every supplement for line numbers before you run marker. `funston2020a-supplemental` (2026-10-14): marker kept all 8,404 words but shifted the reference column of the age-range table by one row for three taxa, and turned a 72.1 into "72.". Word recall cannot see this; compare table rows against the text layer, and check column placement on the page image. `convert_with_vision.py` has no `--supplementary` flag; set `V.PDF_DIR`/`V.MD_DIR` to the supplementary dirs and call `ocr_one_pdf(..., {stem: {}}, stem, log, extra_context)`. It took 41 pp. for $0.57. On 2026-10-14 `intake_discover.py` gained a gutter detector (Path V) and found 19 of 2,157 marker keys with one; all 19 were re-converted with vision and the gutter context (772 pp., $9.65). Against marker's output, everything marker had that vision lacks was noise (Zotero link fragments, words split at hyphens or glued together). `reocr_nooverlap.py` takes no extra context, so pages it recovers transcribe the line numbers; strip them afterwards (rozadilla2020a, 20 lines).

### Science/Nature reprints carry neighbouring articles
Single-article reprint PDFs bundle the tail of the preceding and head of the following article, and marker interleaves them (`curryrogers2016a` held a nitrogenase paper and a cell-quiescence paper around the Rapetosaurus text). It is fluent English, so `intake_qc.py` and `audit_languages.py` pass it. Run `scripts/trim_reprint_spillover.py --all` (bounds the target by its title heading and its own "Correspondence and requests … addressed to" line; refuses rather than guesses). For a manual fix, read the first ~300 chars and `grep -nE '^#'` for foreign headings, delimit by the target's DOI/page in footers, excise with asserts, and record what was cut in `conversion.notes`.

### Spillover the reprint trimmer cannot see: Science, older Nature, shared-page book entries, orphans
`trim_reprint_spillover.py --all` reported "would trim: 0" while 37 Nature/Science files still held a neighbour. Its end marker is the "Correspondence and requests" line, which Science never prints and Nature only from about 1997; it also skips orphan `z` keys (no citation title to match). `scripts/scan_spillover.py` reports what it misses (default scope Nature/Science plus orphans; `--chapters` adds book chapters, where section headings and translated titles make it noisy). The tell is a title-like heading that is not the paper's own; one "Received … accepted" line per Nature letter and one reference heading per paper are the supporting counts.
2026-10-13 cleanup, 41 files: 17 Nature and 20 Science reprints, `swisher1999z`, `shilin1982a` (journal title page, contents and a bryozoan paper in front), `russell1997a` (two `*see*` stubs after an Encyclopedia of Dinosaurs entry), `lucas1995z` (other items printed between the two halves of its reference list, joined by "Continued on p. 17"), after `barsbold1997a`/`smith1997a` the same day. Method: target = own title heading to the next article's title heading (or EOF); check by counting the paper's genera plus "dinosaur"/"theropod" outside the span (0 in most, 1 where a cover sheet repeats the title) and by reading the 90 characters each side of both cuts; slice; record the kept offsets in `conversion.notes`. Science PDFs from the publisher site carry a download cover sheet for the same paper before the title (and once after, `nesbitt2009a`); it holds no body text and goes with the trim. Vision-converted files keep the neighbours in `.runtime/cache/vision/{key}/`, so a vision re-run brings them back.
Before trimming a cited key, give the data agent the spans: it checked every dataset and research-note quotation against them (none sat in removed text) and found `shilin1982a` from its own side. Its quote-position check is a useful second detector but flags monographs with per-chapter reference lists, titles that match an appended abstract, and quotations in appendices; 36 of its 38 keys were those.
Not spillover: `luo1994a` showed two reference headings because of a bad blocked-page recovery; see "A blocked two-column page: OCR the columns, don't stitch halves" below. `salani2007a` held the whole abstracts page; trimmed the same day to the symposium front matter, the target abstract and the Ameghiniana running footer (the data agent asked to keep both as the abstract's bibliographic context), in the markdown and the `.original.md`.

### A marker output folder exists from the start of a document, not its end
While `convert_with_marker.py` runs, `.runtime/tmp/marker_outputs_*/{key}/` is created when marker STARTS a document; `{key}.md` appears only when it finishes. Count documents as done by the `.md` file, never by the folder. On 2026-10-13 an empty `gradstein2004a/` (611 pages, still converting) was reported to the user as finished, and they made a scoping decision on that basis.

### Detached diacritics corrupt two words, and accent-insensitive search fixes only one
Marker sometimes strips a combining mark and re-emits it a few words later. `ezcurra2010a`: "the La Pena, ... and Quebrada ˜ de la Sal members": `La Peña` lost its tilde and `Quebrada de la Sal` gained one. NFKD accent folding finds `La Pena` but still misses `Quebrada ˜ de la Sal`, because the fault there is an extra character.
Scale (2026-09-19): 75 files / 538 occurrences on a strict probe, 102 files / 807 on a looser one; report as "hundreds of occurrences across dozens of files". Worst: `carrano2012a` (89), `oreska2013a` (45), `evers2015a` (32), `pol2024a` (25). Examples: `Pal ¨ aontolo- gie`, `Pos-Graduaç ao em ˜`, `Cern ˇ ý`.
When a diacritic name returns zero, search the stripped form, a form with a stray mark spliced in, and a wildcard across the phrase.

### Dinosauria occurrence tables: read the markdown, never the text layer, and check odd rows
Marker separates the columns of the *Dinosauria* 2nd ed. tables far better than `get_text()`, which interleaves them line by line and invents strings like "Clarens Formation (Free Pliensbachian". Marker isn't perfect: `weishampel2004a` has one real splice, "Kalazha Formation (Xinjiang Tithonian<br>Uygur Zizhiqu)". Detector: `[A-Z][a-z]+\s+\([A-Z][a-z]*\s*(Hettangian|...|Rhaetian)`; across 879 pages it gives 1 true hit and 1 false positive. It is also the acceptance test for any marker upgrade: marker 2.0.0 produced 11 splices on `weishampel2004a` and 2 on `norman2004a`. The bar is v1's single hit, not zero. On the text layer, phrases like "Bushveld Sandstone" are split by newlines, so search a whitespace-collapsed view.

### marker 2.0.0 was trialled and not adopted (2026-09-16)
It was 8.6× faster at workers=1 and 14× at workers=2 (corpus estimate 37.8 h → 2.7 h), and it fixes the MPS worker bug (workers=2 output byte-identical). But it corrupts dense occurrence tables: it re-interleaves columns and joins ages onto place names. Formation+stage row bindings fell 410→335 in `weishampel2004a` and 27→13 in `norman2004a`; 220 files are that dense. `--mode balanced` is worse. It fixes neither the stolen reference-link letters nor the dropped spaces. We stay on marker-pdf 1.10.2. Measurement traps: raw byte counts mislead because v1 pads table cells heavily, so compare non-whitespace content; a rising distinct-word count can mean spaces have collapsed, so count 22+ letter tokens separately. Revisit at 2.1+, with the occurrence-table splice detector as the acceptance test.

## Text-layer font defects: repair mechanically, not by re-OCR

### Elsevier font AdvPS44A44B: en dash extracts as "e", em dash as "d"
This dash-only subset font has no `/Encoding /Differences`, so dashes come out as letters: `BarremianeEarly Aptian` (en dash), `CheloniadPodocnemidoidea` (em dash). The em-dash form is the dangerous one because it yields a plausible single word. The fault is in the PDF's text layer, so neither marker nor re-OCR is the fix. Scope was 80 PDFs; `scripts/repair_dash_font_substitutions.py` fixed 6,108 dashes in 72 files (commit 4f36587). Never fix this with a regex on the markdown: `[a-z]e[A-Z]` matches `ScienceDirect`, and no regex can see the `d` form. The repair keys on the font, replaces whole whitespace-delimited tokens, and has a second pass for bibliography ranges marker turned into links. Thirteen occurrences at other codes were left for review (`$` = ×, `!` = ~, `C`/`D` = ° and δ). Sibling fonts: `AdvPS3FDD77` (`(` = °, `#` = ′) and `AdvP4C4E74` (`¼` = =, `þ` = +). Later batches kept arriving with the fault (7 files and 857 dashes on 2026-10-01, a508f62, including takashima2004a's "CampanianePaleocene"), so the repair is now step 9a of `/intake`, run `--all` on every batch. 2026-10-30, under `PDF_BACKEND=pdfium`: 176 more dashes over 50 files that the PyMuPDF run had missed, applied. 153 were link-split bibliography ranges (`25 e[125]`), missed because PyMuPDF's token for each range held a nearby diaeresis "€" and so never matched the markdown. That second pass used to apply its edits without printing them, so a dry run listed 25 edits while counting 178; it now prints each one ("split by markup").

### Dropped f- and Th-ligatures: scripts/fix_dropped_ligatures.py, gated on the corpus
Some born-digital PDFs decode every f-ligature as a bare "f" ("frst", "signifcant", "shaf", "lef"); the capital Th ligature becomes "T" ("Te Bauru Basin", "Teropoda"). The fault is in the PDF, so a marker re-run does nothing. The script only inserts letters after an existing f. Usage: `--scan` (census), `--audit` (corpus-wide dry run; read it before any bulk apply), `--key`/`--path`, `--apply` (writes `.ligature.bak`). `--all --apply` skips `*.original.md`. Verify a sweep with `git diff --numstat`: added and removed line counts must match. Re-index after applying.
Design lesson: `/usr/share/dict/words` can't be the gate. It lacks "feet" and "floodplain", and a dictionary gate rewrote feet→fleet 3,462 times. Use word counts from clean corpus files, and require a repair to win by 10× where both spellings occur. No entry in a "break signature" list may be a real word in any corpus language ("diferente" is Spanish, "Tese" Portuguese). For Th, lowercase prose is never affected, so the file's own lowercase usage decides. The 2026-08-11 sweep made 12,859 repairs over 222 files. Lexicon cache: `.runtime/cache/ligature_lexicon.json`.

### A small corpus can't be its own ligature oracle: wordfreq mode (2026-11-01)
A new corpus has too few clean files for the word counts above: on a two-paper clean clone, `fix_dropped_ligatures.py` fixed 47 of 141 breaks in a Scientific Reports paper and none of its 75 "Te". Below 500 clean files (`--lexicon auto`) it now uses `wordfreq` frequencies in the paper's language and English, plus a domain vocabulary from the data repo's public data (bib authors and titles, `open-paleo.json` taxon names and descriptions). Measured on the 222 papers of fe77e507 before repair: 98.4% of corpus mode's repairs, no conflicts, and ~330 extra repairs, nearly all real breaks corpus mode refused (fattened→flattened 101, refect→reflect, fanges→flanges, Tanks→Thanks, Tin sections→Thin). Rules that measurement forced, each from a wrong repair:
- The data repo's descriptions contain broken forms themselves ("lef", "afer", "difcult"), so domain words may vouch for a repair but never protect a token as written. Genus and clade names may protect: `Fona herzogae` is not Fiona.
- A capitalised word mid-sentence is protected by any language (Eifel is German, Flament French) and repaired only to a bib name (Bufetaut→Buffetaut) or a very common word (Lef tibia→Left); otherwise Defant→Defiant, Chafetz→Chaffetz. A sentence-initial capital is an ordinary word, but not after an initial ("E. Markgraf").
- No "i" appended at a word's end: that makes Latin epithets (Markgraf→markgrafi, mef→mefi in an email domain).
- In the Th path, count lowercase tokens only: the fault is capital-only, and 55 broken "Tis" outvoted 43 "this".
- An ASCII fragment beside a non-ASCII letter or a spacing accent is judged as the whole word, in every language, in both modes: "geográfca"→"geográfica", but never Lefèvre→"Leftèvre", which corpus mode wrote 137 times in fe77e507 (repaired 2026-11-01, with aérifères, Santa Sofıa and modifïed), or "Pa´lfy"→"Pa´lffy".

### Ligature repair: read the dry run for abbreviations, names and other languages (2026-11-01)
The 2026-11-01 archive pass (corpus mode, 1,212 repairs in 67 papers, two passes: the lexicon changes as papers become clean) kept 19 proposed forms as written after reading them in context. They show what the dry run must be read for:
- figure-legend abbreviations: `fco` fibular condyle, `frm` foramen, `sof` suborbital flange, `afn`, `fna`, `Classif.`;
- place names and other languages: the Moroccan `Rif` (not Rift), German `Fach`, `Feld` ("Im Neuenheimer Feld"), the facies code `Fle`, Spanish split by a space or OCR (`ofre ció`, `mam- ´fero`, `í feros`);
- authors and quoted misspellings: `Foresi et al.`, `*Phytosaurus kapfi* [*sic*]`;
- garbled text where no repair is right: `3-5 flm` (µm), `昀椀fth`, `sh<br>rif<br>he`.

### Nature Adv* fonts read fi/fl/en dash as ®/¯/±
Late-1990s/2000s Nature PDFs (e.g. `AdvPS81DB`) have an empty /Differences encoding, so `signi®cant`, `¯ow` and `north±south` come straight from the text layer. `scripts/restore_symbol_glyphs.py` can't fix this; `scripts/fix_ligature_substitutions.py` fixed 8 keys (curryrogers2001a, ji2001a, martill2000a, sampson2001a, xu1999a, xu2000c, xu2002a, xu2002b). It requires at least three ligature glyphs next to letters, because a spacing macron looks identical (`galton2006a` Ky¯ory¯ugaku, `whitlock2020a`, `peyredefabrègues2016a`). Don't lower that threshold without adding a dictionary gate. A real ± has a space on both sides. Files with mostly free-standing ®/¯ (`reig1963a`, `taquet1977a`, `powell1979a`) have a different defect.

### Dropped symbol glyphs: restore by (font family, glyph name), never glyph name alone
Subsetted symbol fonts (Elsevier `AdvP4C4E*`, `Universal-*Pi`, `MathematicalPi-*`, `Symbol`) extract °, ′, ″, ±, ×, ≤, ≥, ~, en dashes and accents as C0 control characters; marker drops them: `(79°32′, 19°15′)` -> `(7932, 1915)`, `~200 Ma` -> `200 Ma`. No QC detects it.
`scripts/restore_symbol_glyphs.py --all --apply` reads each font's `/Encoding /Differences` (224 keys, 1,588 chars, commit c4716a0). `C##` names are subset-internal: `C21` is a breve in `AdvP4C4E59` and `≥` in `AdvP4C4E74`; keying on the name alone wrote `Rusca Montan≥` 184 times into `díezdíaz2025a`. Verify every new mapping against a ~400 dpi crop.
Accents: `scripts/repair_accent_glyphs.py` (prototype, commit 4f36587, `lindoso2019a`, `ramírez-velasco2022a`, 336 accents) identifies the base letter by bbox overlap (~3.3 pt with its own letter, ~0 with neighbours). Marker renders a dropped accent three ways (absent, a space, or a wrong stray mark like `Universit ~ aria`), and the code->accent mapping is per subset, so each key needs its codes read off crops.

### Locality coordinates lose °/′/″ three ways; only the rendered page tells which
No QC catches a damaged coordinate, because it reads as a clean number.
1. Substitution: subsetted symbol fonts reuse digit glyph names for °/′/″ and `/Differences` corroborates the lie (`AdvP7DA6` prime = `/nine`, `AdvPi1` degree = `/eight`). `25°28′15″N` becomes `258 28<sup>0</sup> 15<sup>00</sup> N`. Recurring: `AdvP4C4E74 '0'` = ′ (doubled = ″), `AdvPi1 '8'` = °, `ESSTIX-Four '(' '#'` = ° ′.
2. Dropped primes: marker keeps ° (as `◦`) but drops ′ and ″ from maths fonts (`MTSY`). The PDF text layer still has them; diff against `page.get_text()` instead of re-OCRing.
3. Scan OCR reading ° as `0`, `'`, `"`, `?`, `•` or the word `go`.
`scripts/identify_symbol_substitutions.py` finds candidates (a character in a coordinate whose font differs from the run's dominant font) and renders a 400-dpi crop; `scripts/repair_coordinate_glyphs.py` holds the verified table, and `--audit` re-finds coordinates by requiring a latitude AND longitude token (pair filter: 89 hits vs 809 for one hemisphere letter).
Some papers print no degree sign at all (`mateus2011b`, `kareem2024a`, `sarigül2016a`, `vickaryous2001a`, `wall1979a`): the markdown is faithful, leave it. `dieudonné2026a` lost primes at typesetting; repaired anyway.

### Elsevier transposed/spacing accents: fix mechanically
Older Elsevier text layers encode accents as base + spacing glyph (`Neuque´n`, `Rı´o`, `Man˜ero`); `leanza2004a` had 772 broken marks and no composed accents. Use `scripts/fix_transposed_accents.py --key K` (dry run) then `--apply`; never vision. The mark can precede or follow its base (`Mus´eum`, `S˜ao`), so the script decides by which letter can legally carry the mark, then by the file's own majority; `--fix-miscomposed` repairs earlier damage (`Solĺe`, `Rodŕıguez`), `--stranded` resolves marks far from their word by corpus attestation. Guards: ASCII `~`/`^` are prose ("~150 km"), backticks are code fences, coordinate minutes (`38°55´S`) need no letter before. Fixing accents can push langdetect over the translation threshold on English papers: check function-word counts and record `translate_skip` + a note.

### CID-garbage detector: short letter runs >45% AND letter fraction <55%
Broken font CID mapping replaces body text with plausible ASCII gibberish. `scan_markdown_quality.py` (fires on PUA/U+FFFD only) and `intake_qc.py` (bytes/page) both miss it. Detector: strip `<br>` and URLs; short-run fraction = runs of `[A-Za-z]` with length <=2 over all runs, flag if >45%; letter fraction = letters/chars, flag if <55%; skip files >2% CJK. Token density is the wrong metric (6/8 false positives on tables and reference lists).
Validated on `suarez-gonzalez2013a`: garbled 72.8% / 8.8%, after vision 24.9% / 74.4%, corpus median 21.6% / 73.8%.
Triage a hit with word recall: take every 8+-letter word in the PDF text layer and count how many appear in the markdown. `ulansky2014a` 4.1% (prose destroyed, re-converted) vs `dias2020a` 96.2% (prose intact, only tables shredded; left alone). Table explosion shreds tables but keeps sentences; CID-garbage destroys prose. Check recall before telling anyone a file blocks work.
Recall checks prose only. If the answer lives in a figure or chart on an image-only page (e.g. `huang2021a` Fig. 3), the PDF is the artifact regardless of the markdown score.
A zero count that is implausible for the paper's own title (e.g. `Enciso` x0 in a paper about the Aptian of Iberia) is the human-visible tell.

### Fullwidth Latin in Chinese journals: finding affected files
CLAUDE.md covers the cause and fix (vision re-OCR). To find cases corpus-wide, a "long space-free run" scan gives ~290 false positives (`infrapostzygapophyseal`, `Naturwissenschaftliche`). Require >=50 co-occurring CJK chars and runs >=30 chars (real long words cap near 22): 290 -> 4. To check a text layer, NFKC-normalise first or count chars in U+FF01-FF5E. After repair, only fullwidth punctuation should remain. Re-OCR can newly surface a translation candidate (`zhou2022a` jumped to zh-cn 54%). Done 2026-08-01: `sekiya2010a`, `lü2005a`, `zhou2022a`, `xu2000b`.

## PDF libraries: PyMuPDF → pypdfium2 / pikepdf / img2pdf (2026-10-30)

PyMuPDF is AGPL, which a permissively licensed `corpus` repository cannot depend on. The scripts bound for `corpus` now read PDFs through `corpus.pdf.text` (pypdfium2 or PyMuPDF, chosen by `PDF_BACKEND`; default `pdfium` since 2026-10-30, `pymupdf` kept for comparison), write image-only PDFs through `corpus.pdf.build` (img2pdf + pikepdf), and copy pages with pypdfium2's `import_pages`. Each port was checked by diffing its dry run under both libraries. What differs and why:

- **Character boxes and sizes.** Use pdfium's *loose* box (`FPDFText_GetLooseCharBox`: font ascent to descent, advance width), which equals PyMuPDF's to 0.1 pt; the default `GetCharBox` hugs the ink. `FPDFText_GetFontSize` is the size before the text matrix (often 1.0): multiply by the matrix scale. Type 3 glyphs have a near-zero loose box (kocsis2013a: 0.2 pt); the helper falls back to the ink box.
- **Reading order around accents.** pdfium does not keep separately drawn accent glyphs next to their letter: it collects them elsewhere (another line, with generated spaces around them) and starts a new line at the font change ("Prieto-M\x01" / "arquez"). Anything that read the mark from text order broke. The helper moves spacing marks back over their letter and drops generated line breaks between glyphs that touch on one visual line; `repair_diaeresis_euro.py` and `repair_accent_glyphs.py` now find each mark's letter by geometry (overlap at least half the mark's width), which works on both libraries.
- **Spaces.** pdfium's spaces are generated (inferred from gaps) and take the font of the text before them; they can sit between two touching letters where a foreign glyph was in text order. Font tallies (`identify_symbol_substitutions.py`) and word building should ignore spaces.
- **Font names.** pdfium gives them in full (`Universal-GreekwithMathPi`; PyMuPDF cut names at 24 characters), and none for Type 3 fonts (PyMuPDF used the resource key, `T1`). `FPDFFont_GetFontName` in this pdfium build returns the substituted system font (Arial for Helvetica): use per-character `FPDFText_GetFontInfo`.
- **Ligatures.** PyMuPDF keeps ﬁ/ﬂ as one character, pdfium expands them. Text-matching repairs verify more words under pdfium (`repair_marker_ref_links.py`: 27 more, all correct).
- **Unmapped characters.** pdfium returns code 0; the helper reports U+FFFD, as PyMuPDF did.
- **Page lines.** pdfium keeps a page number and running head on the same visual line together; PyMuPDF splits them. `identify_symbol_substitutions.py` therefore reports ~100 more mixed-font runs on pdfium over 306 PDFs, all ordinary fonts; every symbol-font finding agrees.
- **Font /Differences tables** are read with pikepdf (`corpus.pdf.text.font_differences`). Pages inherit `/Resources` from the page tree (`Page.resources` follows it); never de-duplicate direct pikepdf objects by `id()`, which repeats. The old regex reader missed `/Differences` stored as a separate object (5 of 306 sample PDFs).
- **Stitched page size.** img2pdf honours an image's DPI, else 96, like PyMuPDF; PyMuPDF used 72 DPI for every JP2 and for DPI declared below 10 (gilmore1924c's PNGs say 0.381), and `corpus.pdf.build` keeps those rules so re-stitches render at the same pixel size. JPEG and JP2 data go in byte for byte.
- **Image extraction.** pdfium decodes 1-bit fax scans to RGB; `extract_pdf_images.py` writes them back at the source depth (1-bit PNG, about half PyMuPDF's grayscale size). Files are now `p{page}-i{n}`: pdfium has no object numbers.

Bugs the comparison turned up in the scripts themselves, fixed for both libraries. `repair_fused_superscript_refs.py` measured "raised" against the lowest box bottom on the line, so a subscript passed whenever the line also held a lower glyph (a symbol-font "=", a neighbouring table row): hernán2018a CO2 ×135, zaffarana2020a SiO2 ×26, yang2008a SiO2 ×19; and nothing stopped ions (hernán2018a Ca2+ ×16, Mg2+ ×17; Fe2+, Sr2+, Al3+ in five more papers). The rule now: horizontal lines only (rotated table headers made subscripts look raised, yang2008a p9); the call's baseline against that of the LAST glyph of the word before it (a span can open on a raised character, demic2012c "Z. FOREMAN2"); the call starting past the word's middle (a kerned hair space overlaps "Hattori1,2" by 1.6 pt); a call split over touching small spans merged ("1" + ",2,6", PyMuPDF on morrison2026a); no charge sign after it. Matching the PDF word to the markdown has fallbacks for how pdfium's text differs: two or three letter runs joined (kerned capitals, "BELLARD IN I"), accent marks removed ("Ro´gers"), shorter endings (missing word space "andFernandoEscaso", or two letters at a capital, "NingLi"), and the call with the markdown's spaces or its first group ("wollastoni10, 11", "Europe3[,18](…)"); a match must be a whole token that ends the call, so "deinonychosaurs6,11" is never cut to "<sup>6</sup>,11" (the old rule did cut corrosion26,27 and therizinosaurs2,9 that way). Measured by applying both versions to copies of the markdown of the 625 papers with edits: nothing the old rule repaired is left unrepaired except ions and units whose minus extracts as "2" ("km3 yr21", "m Ma2"), on both libraries. pdfium then repairs 76 more tokens than PyMuPDF; PyMuPDF's 4 extra are first numbers of calls pdfium gives whole. On the 230-paper venue sample: 14 edits, all author-line calls. 40 random fallback-added edits read: 38 correct, 2 incomplete (chokchaloemwong2019a "aID2" inside an ORCID link marker had already broken; swisher1999z "Cretaceous18±20", ± a mis-encoded dash). The earlier 50-edit read: 50 correct, one incomplete. Known misses: larson2008a's "7" (a superior-figure glyph on the body baseline) and author names set in rotated text. Applied to the corpus 2026-10-30 on pdfium: 3,694 calls over 678 files, only `<sup>` tags added (stripping them gives the old text exactly). A random read of the applied diff then found raised numbers that are not calls, now refused and their 15 files redone: exponents ("body mass<sup>0</sup>.75": no call starts with 0 or precedes a decimal point), isotope mass numbers ("Ar40/Ar39", "87Sr/86Sr", "Nd143": an element symbol with a number in its mass range, 1.8–2.7 × Z, is skipped), and anything next to a slash or hyphened to a word (serrano-brañas2025a's specimen "BENC32/2–0001", eaton1991a's land-survey "SE1/4"). `identify_symbol_substitutions.py`'s `--max-per-key` cut hid runs with symbol-font characters behind runs without (novas2010a's "79(27#E"); they are listed first now.

## Scan OCR damage

### Letter misreads with no digit: `score_ocr_garbage.py --near-miss`
The digit and junk-character signals miss pure letter swaps (`Lambeosavrus`, `Palreontological`, `Fusuisaunrs`). `--near-miss` counts words that occur in at most 2 corpus files but are one deletion away from a word in at least 8, on English paragraphs only. Without that language gate, Czech, Dutch and Portuguese papers top the list on ordinary words. Calibration: seven keys before and after vision re-OCR scored 3.0–53 before and 0.0–2.3 after. Flag at 8; at 5–8 the hits are mostly proper names, so read the printed tokens. The 2026-10-09 sweep over 2,201 non-vision keys: 75 real cases after removing false positives (names, Spanish and Portuguese words, born-digital typos), 1,692 pages, about $31 to re-OCR. Done the same day: 79 keys, 1,730 pages, $31.42, plus about $2 to recover 38 blocked pages. Every key re-scored clean except for false positives: Dutch and Spanish words, place names, the Chinese `1~312` page-range tilde, and an email address. For `mixed_k` on modern papers, rank by digits inside a lowercase word (`d6crit`, `teetl1`, `rod2like`) instead. Isotope and sample labels (`40Ar`, `TTM1`, `SA27`) fill the plain count. Two font faults turned up that look like OCR damage: "2" for a hyphen in Vertebrata PalAsiatica papers (`xu2002c`, `xu2003a`, `xu2004a`, `zhang2001a`) and 鄄 for a hyphen in `xu2010d`.

### Two OCRs disagree on a digit: render the page, don't vote
Both can be wrong on the same glyph, and overall text-layer quality says nothing about a given token. `choffat1901a`: vision 330, Internet Archive text layer 550, the page reads 350 (old faces cut 5 with a flat top bar and 3 with a rounded bowl; on soft scans they converge). `young1942a`: vision "V23a", the otherwise-garbage text layer "V232", and the page confirms V232.
Render the number at 14-16x (`fitz.Matrix(16,16)` on a tight clip) beside an undisputed digit from the same page, stacking all disputed crops into one strip; for a quick look, `d[PAGE-1].render(scale=4).to_pil().crop(...)` and Read the PNG. Narrow the question first ("is the fourth tooth V235?") so one page can answer it, and leave room for an answer outside your hypotheses (here: four teeth under three numbers). Record the repair where a re-conversion will not lose it; for a translated key, write the rule to match both source-language and translated wording (chain is convert -> repair -> translate).

### One letter pair can fail 100% on an otherwise clean scan; repair it in place
`ratkevich1998a` (Sonorasaurus) reads cleanly except the capital "Tu" pair: "Turney Ranch Formation" was wrong 12/12 times in 8 different misreads (`Tlirney`, `Turaey`, `T\irney`, `TVirney`, `Tbrney`...), and "Tucson" 2/2 (`Tbcson`, `Tiicson`). The word was invisible to `search.py 'Turney'`.
Test: count how often the proper noun is *right* in the same file. Zero correct plus several different spellings means one glyph pair failed. Check the same pair elsewhere in the file, confirm the damage is in the PDF text layer, then repair the enumerated variants with a context-gated regex (`\S+(?=\s+Ranch)`) rather than re-OCRing (vision on a clean-facts scan risks fabrication). Do not sweep the corpus on the misread strings: "irney" also matches the surname "Birney de Wet" (lehman2005a).

### Scan OCR reads lowercase l as "/"
Some scans (paleoarchive.com Uppsala Bulletin) give `Euhe/opus`, `Te/eosaurus`, `Pa/aeontol.`, 46× `Vertebrata Pa/Asiatica` in one file. Passes every QC gate but breaks FTS. Detect per key: `grep -oE '[A-Za-z][A-Za-z.]*/[A-Za-z][A-Za-z.]*' | sort | uniq -c`; read the token list, allowlist real slashes (`and/or`, `kg/day`, `Jinlingshen/Yewangzhuang`, specimen numbers like `MPC-D 100/764`), replace the rest, and loop (two faults per word need two passes). Not `scripts/despace_ocr.py` (it only removes spaces, and false-positives on German: `und am`→`undam`). Sibling misreads in the same scans: `MA TEER`, `Mclntosh`, `Vol. Il`→`Vol. 11`, accession stamps over the title line (restore title from the citation).

### Old USGS Professional Paper scans misread capital R as E, K or B
In `sohl1960a` (PP 331-A) and `stephenson1955a` (PP 274-E) 11–25% of "Ripley" read as Eipley/Kipley/Bipley (plus Eiver, Eidge, Kecent). Lowercase r is fine and the prose is otherwise clean, so marker plus a whole-word repair beats vision. Find candidates by listing E/K/B-initial non-dictionary words that become words with R; read them in context first (Keownville and "Key and Biddle" are real). Check the unit name's count before and after. (sohl1960a now has 0 "Eipley".)

### Foreign scan with clean prose but garbled structure: hand-clean, then translate
On rough pre-WWII foreign scans (precedent `janensch1929b`, German Palaeontographica) marker can give clean running prose (5087 umlauts) while the TOC, captions and notation are garbled: ° read as trailing `0` (`45-500` for 45-50°), ½ as `l/,`, specimen numbers split (`dd 11 1`), captions interleaved into prose.
Such a paper can evade `audit_languages.py` (langdetect returned unknown), so "no language flag" does not mean English: count diacritics directly (`re.findall(r'[äöüßÄÖÜ]', md)`).
Fix: conservative cleanup of named artifact classes only (rebuild TOC, ° in angle contexts, fractions, specimen-number spacing, de-interleave captions; never touch prose, leave ambiguous cases), then `translate_markdown.py`. Cheaper than vision re-OCR of prose that is already clean. The user prefers a QC checkpoint before translating rough scans.

### German *gesperrt*: two different failures
German journals (Neues Jahrbuch, Palaeontographica, ZDGG) letterspace the systematic labels (`H o l o t y p e :`). (1) Bad scan OCR garbles letters and spacing (`Hoi 0 t y p e`, `o`->`0`): vision re-OCR fixes the letters. (2) The spacing is real typography, which vision reproduces faithfully: run `scripts/despace_gesperrt.py` afterwards (all-or-nothing, space-deleting only). Then normalise `^Label\s+:` to `^Label:`. `despace_ocr.py` cannot help, since every token is a single letter. Worked example: `galton1980a` (21 runs).

### `despace_gesperrt.py` mis-segments letterspaced species epithets
It re-segments letterspaced runs against the system dictionary, so a letterspaced epithet becomes common words: `p r o r i g e r` -> `pro rig er` (should be *proriger*). Letterspacing is how 19th-century journals set new names, so the damage lands on the most important words and nothing flags it.
Always read the dry-run list; a rejoin into 2-3 short common words is the tell. Fix taxon names by hand. Check first whether vision already de-letterspaced the text (it did on `cope1869c` except one epithet).

### despace_ocr.py guard details
Beyond the CLAUDE.md description: `--apply` writes a `.despace.bak` before the atomic write. Guards block false merges across abbreviations ("see p."), units ("5 m in"), initials, split proper nouns ("the N odosauridae"), and three-token ambiguity ("for th e" → "for the", not "forth e"). A deny set plus a length gate of ≥5 characters (or a safe-short list) stops short words left over from line breaks. Splits where both halves are real words ("for amen" for "foramen") are left alone.

### scripts/resplit_glued_words.py: re-insert spaces a text layer never emitted
Repairs "NewMexico", "KaiparowitsFormation", "Formationis" — the mirror of `despace_ocr.py` (it only adds spaces, never rewrites letters). Glued words pass `intake_qc.py` but break FTS. Gated on the document: on undamaged files it shreds rare words ("steinkern" → "ste ink ern"), so it refuses clean files unless `--force`. Corrected census: 92 files (the first-reported 189 counted files the ungated pass would damage). Usage: `--key K` (dry run), `--apply`, `--scan`, `--audit`, `--all --apply`; lexicon cached at `.runtime/cache/glue_lexicon.json`; re-index afterwards. Never `--apply` blind on Chinese or Mongolian material: on `lucas1998a` about half the proposals segmented romanised names ("Honglishan" → "Hong lis han"). Safe subset there: lowercase→Uppercase boundaries and splits whose left half is a function word (of/the/that/and/in/see/with/from); check "A"/"An" splits in context ("Anearly" = "A nearly").
Lessons for any corpus-oracle repair: build the lexicon excluding files that show the defect (else the glue protects itself), ban one-letter right halves (Latin endings), supply weights for "a"/"I", score recursive lookahead by its weakest part, and add a document-level gate as well as per-token gates.

## Vision OCR

### Vision fabricates plausible tokens; model choice matters
On poor scans Sonnet sometimes writes a name carried over from nearby context instead of `[ILLEGIBLE]` (`young1942a` p8 heading "Szechuanosaurus campi" came out "Chienkosaurus ceratosauroides"). Clean scans also misread epithets while specimen numbers are right (`zhao2008a`: "sinojaponorum"). Checks: verify headings, the genus each page describes, and specimen numbers against a render at scale ≥5; grep a new binomial against the corpus (`grep -rho 'sinojap[ao]norum' markdown/*.md | sort | uniq -c` → 79 vs 2). Fix both `markdown/{key}.md` and the page's cache JSON, or the next cache hit restores the error. Haiku fabricates much more (`bonaparte1984a`: Liassico→"Giassico", which the translator turned into "Upper Jurassic"; `jin2012a`: Hexing qingyi spelled eight ways); do not use Haiku for vision OCR (Haiku 5.5 included; see "Model choice" below). Every vision script defaults to Sonnet via `corpus.models`. When a translated key has a wrong name, diff `.original.md` against the vision cache before blaming the translator.
A born-digital Chinese PDF's own text layer is a full control for its vision OCR. `pang2024a` (2026-10-14) had been vision-OCR'd because marker keeps only its tables (1,233 of 9,432 CJK characters). Aligning the CJK characters of the text layer against `.original.md` (difflib, `autojunk=False`) found 57 substitutions, several of which change the anatomy: 锄骨 vomer→颧骨 jugal/鳞骨 squamosal, 肱骨 humerus→胫骨 tibia, 粗短 stout→细短 slender, 桃核状 peach-pit→棍棒状 club-shaped. Others hit the formation names (灰泉堡→灰紫堡, 助马堡→助马保) and the first author's surname (庞→渑 in every reference). One page also skipped from one 锆石的裂变径迹年龄 to a later clause, which dropped the dated fission-track sentence (73.3±5.6 and 73.5±5 Ma) and printed the summary sentence twice. The image confirmed the text layer at every spot checked. Fix: apply small replace/delete ops where the context matches exactly, fix table cells by hand (cell order differs between the two), then re-translate. Every CJK vision key with a usable text layer can be audited the same way. Latin script has a milder form of the same fault: vision 'corrects' historical spellings to their modern forms. On Bonaparte's 1850 Conspectus (bonaparte1850a) it wrote Gray's synonyms Trionycididae, Typhlopsidae and Cheloniadae as Trionygidae, Typhlopidae and Cheloniidae; the scan's own OCR layer had them right, and the page image confirmed it. Where original spellings matter (nomenclature, synonymy lists, pre-1900 works), compare the set of capitalised names in the vision text with the set in the text layer and read every mismatch on the image. Done the same day with `scripts/audit_vision_textlayer.py` and `scripts/correct_cjk_from_textlayer.py`: 93 more reviewed corrections over nine keys (huang2021a 髫髻山组 Tiaojishan ×11; wang2013c 砾 gravel ×20; huang2005a 舍资组 Shezi; sekiya2010a 眶前窝比眼眶窝长, which had 宽 'wider'). The data agent then caught a second kind the CJK-only alignment cannot see: a dash printed between two characters (中—晚期) read as 一 'one' (中一晚期), 7 places in four keys. `correct_cjk_from_textlayer.py` now proposes those too. Reject layer typos (广范), variant forms (緑, 內), running heads, broken-font glyphs (鄄; 方方土 for 坤) and pairs aligned against different sentences or table cells. Two layers were no control at all: ji2005a and xu2012b use ciphered fonts (digits come out as `$"%`), so their pages were checked on the image.
The same audit found pages vision returned empty or cut short (any language): sotonúñez2026a pp. 29-30 (revised character scorings; output_tokens 0), xu2012b p. 5, ji2005a p. 14. Look for cache pages with output_tokens under ~50 on a page whose text layer is long. And 11 correlation-chart pages the general prompt only described; transcribe those in vertical strips at high resolution with a chart prompt (as for gregory1931a) and label the result.

### Verify vision OCR against the garbled text layer's number multiset
Bad OCR mangles letters far more than digits, so the text layer you are replacing is still a control. Extract the catalogue-number pattern (tune the regex to the series) from the raw text layer and from the vision markdown and diff the Counters: text-layer-only = dropped content; vision-only = fabrication or a caption the layer shredded (look at the page). `gilmore1946b`: 15 USNM numbers, identical sets both ways.

### Image-only scan with no text layer: diff vision against tesseract word counts to find eye-skips
When there is no text layer to use as a control, make one: render each page at scale 3, run `tesseract page.png - --psm 1` (Homebrew, `/opt/homebrew/bin/tesseract`), and diff `Counter`s of `[A-Za-zÀ-ÿ]{5,}|\b\d{2,5}\b` per page (join `-\n` first). Tesseract-only words that are real words, not its own misreads, mark text vision dropped; vision-only words are mostly its `[FIGURE: …]` descriptions and restored diacritics. `serrano-brañas2006z` (5 pp, ~115 DPI): the taxon-page spot-check passed, but the diff found two eye-skips on one page, both jumps between repeated strings: "*Lophorhothon* (Langston, 1960), *Trachodon* (Brown, 1914; …" lost its middle, attaching Brown's citation to the wrong genus, and a 40-word passage between two "Kirkland et al., this volume" was dropped, taking a measurement (356 mm) with it. It also showed vision silently normalising the print ("dinosaurian" → "dinosaur", "corresponds" → "correspond") and omitting the volume-citation header line. A vision-only specimen number is not proof of fabrication: `YPM 618, USNM 4737` looked invented next to tesseract's nearby sentence and were printed two lines later; read the page before deleting.

### A blocked two-column page: OCR the columns, don't stitch halves
`recover_blocked_pages.py` starts every page with top/bottom halves at 20% overlap and only goes to a gutter split if a half still blocks. On a two-column page the overlap band holds text from both columns, the fuzzy suffix/prefix stitch cannot dedupe it, and the result is whole paragraphs twice and out of order. `luo1994a` p. 18 (recovered 2026-08) had its acknowledgements, a fragment of the first reference and a second "## References" heading in the middle of the last body column; nothing flagged it for two months, and it was found only because `scan_spillover.py` counts reference headings. Find them by walking `.runtime/cache/vision/*/page-*.json` in Python for `method == "recovered_split"` (a shell glob over the 21,000 cache files overflows the argument list and prints nothing) and testing each page for a repeated 120-character block or two acknowledgement/reference headings; the backlog is in `open-issues.md`.
Repair: `scripts/reocr_nooverlap.py --key K --page N`, then `--apply`. It tries the intact page, then cuts only on whitespace: columns at the gutter, and a region that still blocks is cut at the blank row nearest its middle (to depth 5; `leidy1858a` p3 needed four bands). Nothing overlaps, so nothing is stitched. It saves a candidate and prints measurements only, never page text. Three things learned on the first 13 pages (2026-10-13; 137 API calls over two passes, cost not logged by the script):
- Sonnet 5.5 still blocks every one of these pages when sent whole; the pieces pass.
- Don't use `column_regions()` for the split. It wants ink on both sides of the gutter in each slice, so a band where one column is short or blank counts as full-width and is read straight across two columns (`lü2008b` p6 came back "6 Conclusion", the other column's references, "6 Conclusion" again). `gutter_zones()` in the new script treats a band as full-width only where ink crosses the gutter.
- A strip holding only a running head or white space comes back as a remark about the image ("No body text is visible in this fragment…"), ten of them in 13 pages. The script drops them; grep any hand-run piece for "fragment".
- Two weaknesses found on the 2026-10-13 batch of 160 pages, both worth fixing in the script. (1) Any ink that crosses the gutter partway down (a figure edge, a stray mark) makes `gutter_zones()` start a new full-width band, which cuts both columns there and yields left-top, right-top, left-bottom, right-bottom: `jain1997a` p12 and `paul2024b` p49 came back with a right-column block inside the left column, and were fixed by hand. The order score catches a large swap; a swap of a few lines can fall inside the 0.03 tolerance. Requiring a crossing band to be tall, or to span most of the width, would stop it. (2) One piece came back as the model's reasoning, `<think>The image is essentially blank…</think>` (`tumanova2000z` p14); the script now strips it. A column cut also leaves a sentence split across two paragraphs when the second piece starts with a capital or a bracket ("in the Middle" / "Jurassic of China"); join those when you see them.
Score a candidate against the PDF text layer, or tesseract where there is none, with two numbers on 4+-letter words: recall (multiset overlap / reference words) and in-order coverage (`SequenceMatcher` matching blocks / reference words). A correctly ordered page has in-order equal to recall; the stitched pages scored 0.54–0.82 in-order against 0.85–1.00 recall, and all 13 repairs came out equal. Word count over reference above about 1.1 means duplication. A repeated-substring test alone misses the out-of-order pages, and "two acknowledgements/reference headings" is not a defect by itself (a page can hold both); check their order.
The same job re-read all 20 pages with Sonnet 5.5 (the 4.6 cache is not model-compatible). Diffing the two readings page by page is a cheap second opinion: 5.5 fixed systematic i/l misreads in taxon names (*Lufengla* ×6, *Yunnanla*, *Dinnetherlum*, *Bienotheroldes*, *Pulengla*), and introduced two errors of its own that only the page image and tesseract settled ("Sues, 1986a" read as "Sues, 1985"; "Olson" pulled to "Olsen" by a misprint in the heading above it). A newer model's reading is not automatically the right one where the two disagree.

### Blocked pages: go straight to reocr_nooverlap.py, single-column pages included
`recover_blocked_pages.py` duplicates text on single-column pages too, not only two-column ones. `owen1855a` (then `owen1855z`, 2026-10-29): all 29 recovered pages carried about 25% extra words, with 95-177 repeated 8-word runs per page. `reocr_nooverlap.py --key K --page N --columns 1` reads such pages from two pieces cut on a blank row, and the word counts come within 1-2% of the text layer. It also accepts a page that is still a `[VISION OCR FAILED ...]` line, so you can skip recover_blocked_pages.py: `owen1856a` (then `owen1857z`, 15 blocked pages) went straight from the failed run to candidates and then `--apply`, with nothing duplicated. The /intake skill section 7 still names recover_blocked_pages.py first.

### Bilingual CJK monographs: --src-lang, then count the CJK left
On a book printed in Chinese and English (`tang2001z`, 2026-10-29), `translate_markdown.py --key K` skips the file ("no non-English language detected"); pass `--src-lang zh-cn`. Even then about 25 body paragraphs came back still in Chinese, with `partial=0` and no warning. They were in chunks dominated by the English half or by tables. Afterwards, count the CJK characters per line outside the reference list and the bilingual figure captions, then translate the leftover lines one by one with `translate_markdown._translate_once` (same model and prompt; 25 lines cost about $0.06). Leave reference entries and the Chinese half of paired captions as printed.

### convert_with_vision.py silently skips already-vision keys
`select_backlog()` excludes keys whose `conversion.tool` is already `claude-vision` even when `vision_ocr_needed=True` (`scripts/convert_with_vision.py` ~line 147). For a replacement re-OCR (new PDF, or after `/extract-pages`), pass `--key K` explicitly; `--force` is a no-op. Check the "Vision-OCR candidates: N" count against the keys you expected. Hit on `owen1874a` and `gervais1852a`. Clear `.runtime/cache/vision/{key}/` first, since the cache key does not include page content.

### Appending pages to an already-converted key: append at the END, never use `--pages`
If the existing pages are cached at `.runtime/cache/vision/{key}/page-NNNN.json` and the new pages are appended at the end of the PDF, merge the PDFs (`fitz` `insert_pdf`) and run plain `convert_with_vision.py --key {key}`: pages 1..N cache-hit and only the new ones cost anything (`seeley1881a`: 84 cached + 5 new, 25 s, $0.12). Inserting pages in the middle shifts every later index and invalidates the cache.
Do not use `--pages` for this: the script builds the markdown from only the selected pages and atomically overwrites `markdown/{key}.md`, so `--pages 85-89` would replace an 84-page conversion with 5 pages. Read a script's write site before trusting a scoping flag to be additive.
For a translated key, the new chunk must also be appended to `{key}.original.md` and translated separately into `{key}.md` (precedent: `huene1929a`, commit 263a092). Update `acquisition.pdf_extract_pages` to the combined range (e.g. `"58-92, 145-147"`).

### Repairing vision pages truncated at the old 4096-token cap
`convert_with_vision.py` now uses `MAX_OUTPUT_TOKENS = 16000` and raises on `stop_reason == "max_tokens"`; the 2026-09-26 repair queue is closed (39 pages, 22 keys). `scripts/reocr_hbands.py` still has `max_tokens=4096` (per band, rarely hit). Traps when using `scripts/repair_truncated_pages.py` or rebuilding a page: pages ≥4090 tokens with a `recovered_*` method sum several calls and are not truncation evidence; an all-whitespace cached page "matches" position 0, so the script inserts into the `[empty page N]` slot; compare re-reads by word overlap (≥85%), not openings; on dense index pages the OLD read may be the fabricated one (`molina-pérez2019a`/`2020a` invented "Bananabenderasaurus"), so check the image and `--accept KEY:PAGE`. For translated keys (`hennig1925a`) repair `.original.md`, translate just that page with `translate_markdown.translate_chunk`, splice into the English. `convert_with_vision.py --key K --pages N` rebuilds the whole markdown from cache, reverting hand cleanups.

### Content-filter blocks: what doesn't help, and the cache entry that's required
Blocks are reproducible per page and occur on both Sonnet and Haiku (~1.4% of pages in the first batch, 8/571); adding "this is a peer-reviewed scientific paper" to the prompt does not help. If recovering by hand rather than with `scripts/recover_blocked_pages.py`, save a synthetic cache entry at `.runtime/cache/vision/{key}/page-NNNN.json`, or the next `convert_with_vision.py` run re-blocks and overwrites the recovered text with a FAILED marker. For 3-piece splits (image+caption on top, two columns below), trim caption fragments that the bottom pieces repeat.

### `scripts/recover_blocked_pages.py` can hang forever on a dead connection
The script calls `client.messages.create` with no timeout or retry. A single page should finish in under ~2 min; if a page shows no progress for over 5 min, check `lsof -p <PID>` for an ESTABLISHED socket with no progress, kill it and re-run (resume-safe; recovered pages are cached). `owen1854b` p.14 hung 51 min, then succeeded in 87 s on retry. Cap it with the Bash tool's `timeout` parameter, since macOS has no `timeout` command. Permanent fix would be `httpx.Timeout(read=120, connect=10)` plus a retry wrapper.

### Check recovered pages paragraph by paragraph, not with sampled windows
A fixed-step window scan (120-char windows every 20 chars) reported no duplicates on `weimer1986z`, yet the seams left a repeated abstract on page 1 and six repeated paragraphs on page 24 (2026-10-08). The overlap copy can also differ by a hyphen versus an en dash. Per cache page: split on blank lines, normalise dashes and whitespace, and drop any paragraph over 80 chars already contained in an earlier paragraph of the same page; apply to the cache JSON and the markdown together. Also rejoin a sentence the seam split (a paragraph starting with ", "). On the 2026-10-09 batch (38 recovered pages over 13 keys) 32 pages had seam duplicates. Paragraph containment removed most of them; a second pass removed any repeated run of 120+ characters outside table rows. The cleaned pages shrank 18–20% and their word counts then matched the PDF text layer. Use that comparison as the check: a page well below its text layer lost content. `coria2002b` p. 5 had 498 words against 676 because its whole right column was missing. Also grep for `[FILTER-BLOCKED PIECE]`: the script leaves this marker where a sub-piece stayed blocked and does not report it as a failure. Fix by OCR'ing that column on its own, halving the crop while it still blocks. `barrett2002a` carried one such marker until its p. 17 was re-read on 2026-10-13.

### Do post-recovery dedup without printing recovered page text
The content filter applies to Claude's own output. Running `recover_blocked_pages.py` is fine (its API calls are out-of-band), but echoing the recovered page text into the conversation while checking stitch boundaries re-trips the block (paul2024a, 26 blocked pages of predatory-dinosaur art). In the main loop, run dedup scripts that print only page numbers and char-count deltas; delegate anything that has to read or show the content to a subagent. Note: the `/intake` skill's "eyeball the recovered pages" step should be read in this light.

### Map recovered pages by the cache string, not by splitting on `---`
Recovered page text can contain its own `---` rule, so splitting `markdown/{key}.md` on `"\n\n---\n\n"` gives more segments than pages and shifts every index; the dedup then runs on the wrong text and reports clean. `jain1997a` (24 pages) split into 25 segments; the index-based pass said clean, the cache-based pass found 3,006 chars of duplication. Locate each page by its cache JSON `markdown` value, `assert md.count(t) == 1`, splice back by value with `md.replace(t, cleaned)`, and rewrite the cache entry. Sanity-check first: segment count vs PDF page count.

### recover_blocked_pages vertical splits and reocr_hbands
A vertical sub-split cuts every line of a single-column page; the output is a column of sentence stubs that passes all QC. Detect via the vision cache: `method == "recovered_split"` pages with mean line < 80 chars over 40+ lines (real 19th-c. pages run 150-450). Never run a longest-repeated-substring dedup on these (it deleted ~1.9 KB from `cope1868a`). Fix with `scripts/reocr_hbands.py --key K --page N` (full-width horizontal bands; `--bands 6` cleared all 42 filter-blocked quarters for $2.42). `recover_blocked_pages.py` now bands single-column pages (`column_regions()`), with gutter detection requiring ≥20% ink on both sides (`jin2012a`). `reocr_hbands --columns auto` can also shred a two-column page (`gao1999a` p5): check word-order SequenceMatcher against the text layer (>0.95) and scan for runs of 2+ lines under 12 chars; fix with `--columns 2 --bands 4`.

### Rebuilding markdown from the page cache reverts cleanup
`rebuild_markdown` regenerates from the raw per-page cache, reverting `strip_frontmatter.py` and `strip_running_heads.py`. Run those last, after the final rebuild, and check for `markdown/{key}.original.md` before rebuilding a translated key. `strip_running_heads.py` is unusable on index-heavy books (on `paul2024a` it wanted to cut 2,938 index lines); remove real running heads by hand there.

### Conference posters: hand-repair after `scripts/tile_ocr_poster.py`
Always `--dry-run` first to check the tiling plan and DOWNSCALED flags. If only the two outer margins are detected as gutters, the title banner is masking them (`--top-frac`, default 0.08). Two artifacts always need hand repair: the title fragments across title tiles and must be reassembled from the pieces; a heading in a row-overlap band is transcribed twice (`sort file | uniq -d` finds it). Verify against the rendered image. Worked example: `dalman2011z` (13 tiles, ~$0.30). Key posters as `{author}{year}z`.

### Model choice: Sonnet for OCR and all translation; Haiku 5.5 is not used
Tested 2026-10-07, the day Haiku 5.5 (`claude-haiku-5-5`) was released, against Haiku 4.5 and Sonnet output on pages where Haiku 4.5 had failed:
- **European translation: Sonnet, reversed the same day.** The first real Haiku 5.5 run (`furrer2025z`, German, 2 chunks) returned chunk 0 mostly untranslated: 21 of 37 long paragraphs still German, with `end_turn` and a length ratio of 0.97, so no guard fired. It also wrote *Acrodus* for the printed *Acrodonchus*. Detect this with a function-word count per paragraph (`und|der|die|das|wurde|von|nicht|mit|ein`, five or more), not with the length ratio. Before that run, a `svoboda1989z` Czech chunk had looked better than Haiku 4.5. It translated a German summary that 4.5 left in German, and gave "Veliké Vsi" as Velká Ves (4.5: "Velika Ves"). It costs about an eighth as much per chunk despite the new tokenizer's ~25% more tokens: $0.10 / $0.50 per MTok below 100K prompt tokens, which every chunk is.
- **CJK translation: still Sonnet.** With `CJK_TAXON_RULE`, Haiku 5.5 gets 晓龙 → *Xiaosaurus* (without it, *Xiaolong*), but on `dong1983b` it gave 大地龙 as "*Dilong* (?)" where Sonnet gave *Tatisaurus*.
- **Vision OCR: still Sonnet.** Haiku 5.5 fixed both Haiku 4.5 failures (`bonaparte1984a` "Liassico", `jin2012a` *Hexing qingyi* spelled one way). On 10 pages, though, it misread `jin2012a` *Beishanlong* as "Beishanglong" and JLUM as "ILUM". It also "corrected" the printed *Brachyosaurus* to *Brachiosaurus* (`bonaparte1984a` p. 134) and "correllation" to "correlation" (`cope1869b`). Sonnet made none of these errors. It also closes up letterspacing and drops running heads, neither of which matters.

**Both models substitute well-known taxa for less familiar printed ones.** In `furrer2025z` the page prints "(?*Abrictosaurus* sp.)"; Haiku 5.5 and Sonnet both translated it as *Lycorhinus*. After any translation, list the italicized names in the output that don't occur in `.original.md` and check each against the rendered page. Text-layer misreads ("Gaumia lincisa", "Termatosaurus albertif") show up in the same list and are legitimately corrected.

Haiku 5.5 thinks by default, and the thinking counts toward `max_tokens`; `models.request_extras()` turns it off. Sonnet 5.5 rejects `{"type": "disabled"}` with a 400, so the helper sends it only to Haiku. The SDK is pinned at `anthropic==0.46.0`, which predates the `thinking` parameter, so it goes through `extra_body`. Both models can stop with `stop_reason: "refusal"`; `translate_markdown.py` treats that as a failed chunk and doesn't cache it.

### Changing the pipeline's models
`corpus.models` (`src/corpus/models.py`) holds `SONNET`, `HAIKU`, `CACHE_COMPATIBLE`, `PRICES` and `request_extras()`. Haiku 4.5 translation caches are cache-compatible with Haiku 5.5, but not with Sonnet, so re-running a key first translated on Haiku re-translates every chunk on Sonnet; to keep the old chunks, pass `--model claude-haiku-5-5`. Every cache (vision, translation, tile, specimen) reuses an entry only if its model is cache-compatible, so a bare constant swap would make any rebuild re-OCR every page. For the next change: confirm the ID on GET /v1/models, change `SONNET`, add the new ID to the same `CACHE_COMPATIBLE` group and to `PRICES`, then test that `cached_page_response` hits on an existing key's page. Per-page cost estimates (~$0.017–0.028) came from Sonnet 5 runs logged at $3/$15. Sonnet 5 and 5.5 actually cost $2/$10, and costs logged before 2026-10-07 overstate spend by about 1.5×. Check `PRICES` against the pricing page whenever a model changes.

## Translation

### The language audit over-reports foreign content; re-measure per paragraph
`scripts/audit_languages.py` runs langdetect over the whole document and flags at ≥25% non-English, which is unreliable on mixed-language papers. Re-measure by splitting on blank lines, detecting each paragraph over 120 chars, and summing characters per language. Of seven "real candidates" checked on 2026-09-08, three were English papers: galton1981a (audit fr 51%, per-paragraph en 84%), bellardini2023a (es 37% → en 87%, Spanish affiliations), taquet1998a (fr 34% → en 74%, French *Version abrégée*). Translate only when the foreign language is the majority of body paragraphs; otherwise confirm the English text carries the type specimen, locality and diagnosis and leave it.
Expect this from Comptes Rendus (English + *Version abrégée*), Geobios, Ameghiniana, Revista Brasileira, Cretaceous Research with Iberian authors, and the ICZN Bulletin.
Order of checks: CID garbage → OCR fix → language verdict. `handa2012a` read "fr=31%" whole-document and "de=11%" per paragraph; neither was real. Its body font shifts every character by +29 and drops spaces (`7KHPDWHULDOV...` = "The materials..."; leading digits stand in for capitals: `7KH` = The, `03&` = MPC). `scripts/intake_qc.py` (3849 B/page) and `scripts/scan_markdown_quality.py` both passed it because the garbage is plain ASCII. Do not try to decode the shift: italic and bold runs come from a working font, so a blanket +29 corrupts them. Vision re-OCR fixed it (21 pages, $0.60).

### `audit_languages.py --key` rewrites the whole TRANSLATION_AUDIT.md
`--key` narrows the scan, not the report write: the report comes out containing only that key, deleting every other entry (seen on the `tang2001b` intake, -87 lines). Run it without `--key`, or run it with `--key` and then `git checkout -- TRANSLATION_AUDIT.md` before staging. Always `git status` after the QC block.

### Bilingual papers: force the source language
Papers with a CJK/Russian/French body and English title/abstract/captions/references defeat the 15% language gate in `translate_markdown.py` (`huang2005a` was 31% CJK yet detected as `en`; `ji2022a` had zh-cn at 14.3%). After eyeballing the body, run `--key K --src-lang zh-cn`, one key per run (the flag applies to every key). `scripts/scan_markdown_quality.py` counts CJK characters and is the more reliable detector for these. Bilingual captions (`图1 …` + `Fig. 1 …`) legitimately survive translation; leave them.

### Translation can leave one chunk untranslated while reporting ok
`scripts/translate_markdown.py` can return one chunk that echoes the source while reporting `ok=1, partial=0`. Count residual source-script characters (Russian: `'а'<=c.lower()<='я'`); a few is normal (figure letters, references), thousands clustered mid-document is a missed chunk (`tumanova1987a`: 2227 Cyrillic chars at ~78% through). Re-translate only that block and splice it into `{key}.md`; leave `.original.md` untouched.

### Verify translations by per-section ratio and invariant counts
The 50% whole-file length gate misses mid-document loss. Compare sections matched by heading text (not by position — the translator changes heading counts): ko/zh→en run ~1.7-2.1×; a section at 0.5-0.6 lost content (`kwon2013z`: 1.31 overall, section 4.5 at 0.57). Also compare `[FIGURE:` counts and `^|` table-row counts between `.original.md` and `.md` (`jenny1981a`: figures 6 vs 4, rows 17 vs 8; `hennig1915a` dropped Figs 5 and 7 with specimens St 297/461/77/856 at an overall 0.93), and the catalogue-number multiset. Grep for model false starts ("Wait, I need to", "Let me redo"). To redo one bad chunk: re-chunk `.original.md` with `translate_markdown.chunk_markdown`, compare to `.runtime/cache/translation/{key}/chunk-NNNN.json`, delete only that chunk's JSON, copy `.original.md` over `{key}.md`, re-run. `MIN_CHUNK_RATIO = 0.8` now retries/fails short non-CJK chunks, and `clean_chunk_opening()` strips chunk-opening artefacts. Check formal unit names afterwards ("Poudingue fleuri" became "Flowering Pudding"); restore the original forms.

### Bilingual figure captions: the translator drops them, and the chunk fails as short
Brazilian journals (Derbyana, Geociências, RBP) print every caption twice, in Portuguese then English. On `arai2023a` the translator kept one copy on a good run (chunk at 0.78) but dropped every caption, Figures 8–13, on later runs (0.61). The `MIN_CHUNK_RATIO` retry then rejects the chunk, and every re-run re-translates it and overwrites the cache, so a version you checked can be gone on the next run. Lowering the threshold won't help, because the short version really did lose content. Fix: translate the failing chunk in about three paragraph-boundary pieces with `translate_markdown.translate_chunk` (each piece kept its captions), join them, write the result as `chunk-NNNN.json` with `hash=chunk_cache_key(src)`, delete `chunk-NNNN.short.json`, and re-run the script so it assembles the paper and updates the manifest. Check by caption numbers (`FIGURE n` present once each), not by length. Residual-Portuguese counts will flag "São" in place names; that is a false positive.

### The translator can skip the opening of a chunk, and a cache rebuild loses hand repairs
On `hennig1925a` chunk 6 the translation began at the chunk's first `#` heading ("III. Descriptive Section"). The prose before it and the whole 1900+ bibliography were gone, about 10,500 characters at a 0.37 ratio. `moser2003a` chunk 13 skipped Dehm's and Urlichs's field profiles in the same way. A chunk that opens with a table (a contents page) often comes back without the table (`moser2003a` chunk 1, `tumanova1987a` chunk 12). That is harmless in itself, but until 2026-10-09 `clean_chunk_opening()` then deleted the chunk's prose while looking for the table: 51 lines of `moser2003a`'s introduction. To see what is missing, print the translated chunk's first paragraphs next to the source's. Matching paragraphs by capitalised tokens fails on German. Fix by translating only the missing slice and splicing it into `{key}.md`. Do not rebuild `{key}.md` from the chunk cache: hand repairs live only in the markdown (`hennig1925a`'s spine-measurement table, `tumanova1987a`'s re-translated chunk 10), and a rebuild silently reverts them. Find a chunk's span in the markdown by the tail of the previous chunk and the head of the next. Also remove the model's invented opening headings ("# Translation", "# Paleontology Translation", "# [BEGINS TRANSLATION]"). 45 of them over 29 keys were deleted on 2026-10-09, and `clean_chunk_opening()` now drops them.

### Translations leave the reference list untranslated by design
`translate_markdown.py` keeps cited titles in the source language so they stay findable (`zhao1991a`: 509 CJK chars, all in the references, zero in the body). When judging a translation by residual source-script characters, split body from references first.

### Chinese translations drop 上/下 from formation names
上沙溪庙组 / 下沙溪庙组 are the Upper and Lower Shaximiao Formations, separate units; the translator can render them as bare "Shaximiao Formation" or turn 底部 ("base") into "lower part". `li2009b` p. 1203 (no `.original.md`; the Chinese is only in the PDF text layer) had five such errors in one sentence, including "the lower part of the Shaximiao Formation at the Yongchuan Reservoir" for 重庆永川上游水库上沙溪庙组底部, the base of the Upper Shaximiao at the Shangyou Reservoir (reported by the data side, 2026-10-04; fixed in the markdown). Before citing a horizon from a translated Chinese paper, check the unit name against the text layer (`pypdfium2`, grep the Chinese), and grep translations for bare "Shaximiao Formation" next to a place name. A corpus scan on 2026-10-04 (every PDF with a Chinese text layer: count 上/下沙溪庙组 and 上/下禄丰组 against the English) found the same fault in four more keys, all fixed: `dong1977a` ("Upper Cretaceous Shangxiamiao Formation … Callovian" for 重庆群上沙溪庙组 … 晚侏罗世早期, early Late Jurassic), `dong1982a` ("Xiasha Stream Formation" for 下沙溪庙组, "Chabcha Formation" for 察雅群, the Chaya Group), `huang2014a` ("Dashanpu Formation" for the Lower Shaximiao at Dashanpu) and `he1984b` (dropped "Middle" Jurassic). `li2009b` also called its own genus "Jianweiasaurus" (犍为乐山龙 is *Leshansaurus qianweiensis*). Untranslated Chinese markdown (`sekiya2010a`) and keys whose counts matched (`li1982a`, `pang2002a`, `zhu1994a`, `hu2023a`, `dong1983b`) were left alone. The scan covers only these two split units; other 上/下 pairs were not checked. Further translation slips reported by the data side (2026-10-04), fixed: `wu2013a` "Qike Town" for 七克台镇 (Qiketai); `dong1984a` "Qilixi" for 七里峡 (Qilixia, ×4); `martínez1986a` "the hind limb of the Bajo Barreal Formation" for *miembro inferior* (the lower member). Spanish *miembro* is both "limb" and "member"; grep Spanish translations for limb/leg next to a formation name.

### Translation on top of garbled OCR: re-OCR, don't patch numbers
When marker's OCR shattered digits and the text was then translated, the translator reconstructs every number and sometimes guesses. `zhu1994a` (Yingshanosaurus) had seven wrong values; checking against the source text layer found four, re-OCR found seven (e.g. metatarsal II 57→87, coracoid 60→600, column header "width" was 高 = height). Re-OCR then re-translate ($0.39 for 7 pages), verify each changed value against a rendered crop. Delete stale `.original.md` and translation cache first. Signature: `conversion.notes` mentions translation on a `tool: marker` entry whose PDF is a pre-2000 scan.

### Delete .original.md before re-translating a re-OCR'd key
`translate_markdown.py` writes `markdown/{key}.original.md` only if it does not exist ("first translation"). After a replacement re-OCR, the old backup survives silently and no longer matches the new English. Before re-translating: `rm -f markdown/{key}.original.md` (and clear `.runtime/cache/translation/{key}/`, whose hash-keyed chunks would replay the old text). Detector: after translating, `git status markdown/{key}.original.md` must show modified. If forgotten, rebuild it by joining the `markdown` field of each `.runtime/cache/vision/{key}/page-*.json` with `\n\n---\n\n`. Missed this four times (janensch1920a, haubold1990a, once reported as fixed when it was not, and meyer1861a on 2026-10-09, after the BHL re-OCR).

### After any bulk re-OCR, audit stale translation backups — but read before deleting
Root cause seen four times: `translate_markdown.py` ran on a broken marker conversion, backed that up as `.original.md`, then vision OCR replaced `markdown/{key}.md` while the stale backup and `translated_*` fields survived; `translated_from` was langdetect noise on garbage (`brett-surman1979a` "fr" on an English Nature paper; `you2008a` "de" from CID garbage). Sweep for keys with `conversion.translated_at` whose `.original.md` is absent or tiny, then read each backup: `sternfeld1911a`'s 1,782-byte backup is a legitimate one-page German note. Surviving `haiku` strings in manifest notes (`moser2003a`, `zhu1994a`) are the translation model, not OCR; no Haiku OCR remains.

### Translation cache directories may sit under pre-rename keys
`.runtime/cache/translation/*/` directories can carry old orphan names (`wang2013z/`, `xue1996/`) while the live keys have an a/c suffix. Resolve a cache dir to its live key by hashing its `original.md` against `markdown/*.original.md`, not by directory name.

### Some markdown files are human translations; re-converting destroys them
`powell1979a` (Powell 1979, Ameghiniana) and `reig1963a` (Reig 1963, Ameghiniana) are published human English translations by Matthew Carrano, originally `.doc` files. `/intake` on a replacement PDF overwrites `markdown/{key}.md` unconditionally.
Before re-converting a key whose `conversion.tool` is `textutil-markdownify`, read the first 500 bytes for a "translated by" line. Preserve both: convert, move the result to `{key}.original.md`, restore the translation to `{key}.md`, set `conversion.original_markdown_path`, `conversion.translation = "human (<translator>)"` and `conversion.notes`.

### Large foreign monographs: present cost and quality, let the user decide
Do not bulk-translate a ~100+ page foreign monograph by default. Cost is the weak argument (moser2003a, 188 pp German, was $1.37 with Haiku) and the skip was reversed on request. The durable concern is that nobody proofreads 188 pp of machine-translated anatomy. Completeness is verifiable (source function-word counts before/after, failed-chunk markers, size ratio, survival of taxa/specimen prefixes/formations); correctness of technical terms is not. Offer the middle path: translate only systematics/diagnosis/description sections. Always confirm `markdown/{key}.original.md` exists and commit both files. Check pricing via the claude-api skill, not memory.

## Cleanup scripts

### Rotated "Journal Pre-proof" watermark lands one letter per prose line
On Elsevier pre-proof pages without a table, marker glues one watermark letter to the front of each prose line (`f o lambeosaurines…`, `r p Our osteohistological…`); read downward the letters spell "Journal Pre-proof" backwards with gaps. Shape cannot gate this: affiliation superscripts (`a Institut Català…`), sentences starting with "A", and `A B S T R A C T` look the same (all in `fondevilla2019a`). `strip_preproof_rotated()` in `scripts/strip_frontmatter.py` chains candidate lines (gap ≤ 4, chain ≥ 5) and cuts only when the letters are a *subsequence* of `JOURNALPREPROOF` in either direction (marker drops letters). Trailing-edge letters are deliberately left alone (a trailing "a" is indistinguishable from prose).

### Shredded "ACCEPTED MANUSCRIPT" watermark vs shredded rotated table headers
On Elsevier accepted manuscripts with a table, marker can read the watermark one letter per row (`| T<br>Zhu et al., 2007 |`). Rotated column headers shred identically: "Characters in Xunmenglong" (`xing2020a`), `R<br>A<br>D<br>I<br>U<br>S` (`díezdíaz2018a`). `scripts/strip_frontmatter.py` gates on two things: the rest of the cell has no further `<br>`, and `_is_watermark_run()` requires a contiguous slice of "ACCEPTEDMANUSCRIPT" forward or reversed. Never strip a lone capital (character tables use one-letter presence codes). Verify a sweep by character multiset: diff against `git show HEAD:file`, assert nothing added and every removed char is in the watermark alphabet plus `<br>|` whitespace.

### Extending strip_frontmatter.py: anchor rules learned per publisher
- Anchor on the FIRST cover match and extend over the contiguous short run; a "last match in HEAD_LIMIT" rule cut the title and author from `ostrom1970a`, a facsimile that reprints the original Peabody colophon. Print the resulting head of every affected file, not just the removed blocks.
- Some covers are not head prefixes: Palaeontologia Electronica and PeerJ put licence/sidebar text after the abstract → paragraph denylist (`PHRASE_JUNK`), anchored `^…$`. PeerJ DOI pattern pinned to `10.7717` (301 files cite a PeerJ DOI; only 58 carry the sidebar). Do not strip "Corresponding author <name> <email>" (it is real metadata in e.g. `alcober2010a`). Keep ZooBank LSID headings.
- Elsevier/ScienceDirect masthead has a headless variant (marker drops the "Contents lists available at ScienceDirect" anchor): fallback requires the run start at block 0 and the homepage line to name an Elsevier domain (bare "journal homepage:" is also T&F).
- Iterate `--apply` to a fixed point (one pass took four: 68 → 7 → 1 → 0 files), and audit diffs by net-removed lines — the stripper normalizes a missing trailing newline, so raw `-` lines overstate deletions.
- Left uncovered on purpose: Science Advances' end-of-paper dates (past HEAD_LIMIT), `cincotta2019a` (sidebar 11 chars past the limit). Do not raise HEAD_LIMIT globally.
- Handled covers so far: T&F ×3, BioOne, JSTOR, Elsevier AM, Elsevier published + headless masthead, BHL, Royal Society, UMI/ProQuest, ZORA, UAB DDD, EBSCO, eScholarship, Yale Peabody/EliScholar, Palaeontologia Electronica, PeerJ.

### Gutter-manuscript audit: re-run after intakes; four keys are known boilerplate
`scripts/audit_gutter_manuscripts.py` measures how much of a line-numbered manuscript's text layer failed to reach marker's markdown; exits 1 above threshold. Read the `examples` before acting. Do not re-flag `eberth2020a`, `gates2021a`, `yin2026a`, `yin2026b`: their loss is publisher boilerplate (gates2021a loses 12.3% of lines to a per-page "(c) the author(s) … Draft" header, ~2.6% real content). Expected residual false positives on already-fixed keys: character matrices rendered as tables (`sotonúñez2026a`, `xing2020a`), legend/lithology-key text (`widlansky2018a`), and a split "Confl icts of interest" line (`park2019a`).

### Word files: textutil drops automatic list numbering
`convert_doc_to_markdown.py` (textutil -> HTML -> markdownify) loses Word's automatic numbering, in both HTML and plain-text output. In a character list that is a real loss, because the matrix columns map to the numbers. canale2009a-supplemental.doc: 113 characters arrived unnumbered; they were restored in order after confirming the count matched the matrix width (113), and the restoration is noted in the file. After converting any .doc/.docx with a numbered list, count the items against what they index (matrix columns, figure references) before restoring numbers; if the counts disagree, do not guess.

### Marker over the memory limit: split the PDF before falling back to vision
Marker's memory grows with the document, so a long born-digital PDF can pass the 9 GB watchdog even when each page is ordinary. gorscak2016z (a 471-page dissertation) was killed whole, but went through as 8 parts of 60 pages, each in its own marker process with the usual flags and watchdog (peak well under the limit, ~3 min per part), joined in page order: word recall 0.998 against the text layer. This is free, where vision on 471 pages is ~$10. Split with PyMuPDF `insert_pdf(from_page, to_page)` into separate directories, run `marker DIR --output_dir ...` per part, concatenate, and write the manifest `conversion` block by hand (tool `marker`, notes saying it was chunked). Earlier keys sent to vision for this reason (gregory1931a, fang2016z, ning2024z, cohen2013a, denne2016a) could have gone this way.

### Italic z with a descender reads as x
In the italic of early-1900s German antiqua (Gustav Fischer, Jena), z has a descending tail and looks like x at normal resolution. Vision read *Thecodontosaurus polyzelus* as "polyxelus" 14 times in huene1914z, and the scan's own OCR mostly did the same, so agreement between the two proves nothing here. Settle it by cropping every occurrence at scale 6-10 using the text layer's character boxes (`get_charbox`) and comparing the glyphs side by side; then fix the vision cache and the markdown together, before translating. Expect it in italic species names containing z (*polyzelus*, *zitteli*, *franzi*).

### Marker can stack two table rows into one and pair values with the wrong specimen
rich2014z (Alcheringa 2014, T&F), Table 1 over five pages: marker put two or more rows into each cell with `<br>` ("Centrosaurus<br>Centrosaurus | MP 67.20.29<br>MP 91.18.23<br>RT<br>RT"), split prefixes ("RT" + "MP" for RTMP), and the stacked value cells no longer lined up with the stacked specimens. Every specimen number was still somewhere in the file, so a presence check passed; word recall (0.915) was the only hint. Detector: table cells holding `<br>` in more than one column of the same row. Fix: transcribe the table from the page images one page at a time with a fixed column list, then compare per page the multiset of numbers and of words with the text layer (only headers, running heads and page numbers should differ), and splice it over marker's blocks. Marker may also emit the continuation pages' blocks out of order, so locate them by the "Table N. (Continued)" captions rather than assuming one block.

### Character matrices: marker can drop whole taxon rows
zanno2009a-supplemental (2026-10-19): marker kept 61 of the 76 taxa in the plain-text data matrix and silently dropped 15, including the paper's own new species; word recall was still 0.996, because the names survive elsewhere in the file. For any supplement with a matrix, parse the matrix from the text layer (taxon line followed by coding lines; codings may contain `(0&1)`-style polymorphisms and taxon labels need not be binomials, e.g. "EK troodontid (IGM 100/44)") and check that every taxon is present and every row has the same character count. If marker's version falls short, replace the section with the text-layer rows (one backticked coding line per taxon) and say so in the file.

### Vision adds series digits to Chinese unit symbols (ling1996z, 2026-10-22)
Chinese stratigraphy papers print formation symbols as K or J with a subscript
letter only, e.g. 茅店组(K<sub>m</sub>), 周田组(K<sub>z</sub>). Vision OCR
"normalised" all eight in ling1996z to series-digit forms (K₂m, K₂t, K₁l)
and read the subscript z as a 2 (K₂). That turns a lithostratigraphic symbol
into an age claim the paper doesn't make. Found by data-agent-strat against the
page images. In these papers, check every unit symbol against the page and
write subscript letters as `<sub>`, since Unicode has no subscript z. The
same paper also lost a syllable from a genus (Pseudococypris read as Pseudocypris).

### Re-converting a translated key: translate_markdown.py keeps the old .original.md
`translate_markdown.py` writes `markdown/{key}.original.md` and `.runtime/cache/translation/{key}/original.md` only if they do not exist yet, so after a replacement re-conversion (Path D) both still hold the previous version's source text while `{key}.md` is the new translation. Found on nopcsa1929a (2026-10-23: a 9-page partial replaced by the 85-page fascicle; the .original.md stayed at the 9-page German). The chunk cache is safe (hash-checked per chunk). After any re-translation of a replaced key, rewrite both originals from the new source (for vision keys, the cache pages joined with "\n\n---\n\n"), or delete them before translating.

### "€" for the umlaut: T&F/Wiley/Elsevier fonts extract the diaeresis as the euro sign
Some publisher fonts map the diaeresis glyph to "€", and marker passes it through, either before its vowel ("M€uller", "f€ur", "pro€otic") or detached ("Lu, J. €", "Eotv € os", "Follmi, € 2012", "Pal € €aontologie"). 2026-10-24: 144 markdown files carried it (fonseca2024a 86, rocchi2026a 165). `scripts/repair_diaeresis_euro.py --all [--apply]` reads the fix from the PDF by glyph position (since 2026-10-30; text order differs between PyMuPDF and pdfium, so a map built from it broke on pdfium): each "€" is drawn over its vowel, the vowel is the letter under the mark's centre, and the word is read off that line by x, a word ending where the gap exceeds 0.15 × font size. That gives the map entry (Hubner -> Hübner); in the markdown it removes a "€" only when the word it sits in, the word it splits ("Eotv € os"), or a mapped word within 12 characters can be umlauted, and leaves everything else. A dry-run invariant (strip diacritics, "€" and whitespace: old == new) held on all 121 files; 726 marks repaired over 78 files. Left for review (449): (1) "€" that marker wrote for an acute accent, which the PDF encodes as a control character ("Lor\x01and" = Loránd, markdown "Lor € and"); (2) marks inside Elsevier reference-link markup where marker broke the word across link brackets. Real euro signs are untouched (no vowel under them). "€" in `GlyphLessFont` (the invisible OCR layer on scans) is skipped: it is OCR noise, and mapping it umlauted scans at random (welles1984a "thë", hatcher1907a "Äfter", gilmore1914b "THRÖUGH"). **Bug in the 2026-10-24 run (4d589f7):** its post-fix clean-up stripped every space before `,.;:)]` in the 40 characters before each repair, not just the one the mark left, removing 357 spaces in 47 files. Nearly all were stray spaces ("Ankylosauridae :"); the 8 that mattered (`a .tnt file`, `.xlsx`, `.obj`, `.newick`, `3D .pdf`, and kumar2022a `S .dunaii`, an OCR slip now written *S. dunaii*) were restored 2026-10-30. The clean-up now only touches the repair site. Rerun 2026-10-30 under both backends: 21 more marks over 8 files, identical on both. Faithful to print: fonseca2024a's "Sänchez-Villagra" is the journal's own misprint; Gilmore 1931's "troödont" is correct.
Related, larger and not yet handled: the same PDFs encode other accents as control characters before the vowel (\x01 acute in most fonts, \x02, \x03, \x13 vary by font: "Sebasti\x01an", "Mus\x02ee", "M\x13arquez"); marker usually drops these, so the markdown shows the bare letter.
Run the repair on each intake batch, like the Elsevier dash repair.

### Word state lists numbered from 0, and matrix rows that wrap across page ends
madzia2019a-mmc2.docx (2026-10-24): the character states are Word auto-numbered lists whose level has no `w:start`, so per the OOXML spec they count from 0, matching the matrix codes. textutil drops all automatic numbering (see "Word files: textutil drops automatic list numbering"), which would have left 376 states unnumbered. Converted instead straight from `word/document.xml`, writing each list number (counter per numId, starting at the level's `w:start`, default 0). Check after any such conversion: characters complete, each state list 0..k, matrix width = character count.
huang2026a-supplemental (TNT xread, 231 x 108): marker treated a gap '-' ending a coding line at a page break as a hyphen and joined the lines without it (4 rows one short), and placed one taxon label a line late, moving 91 codings to the previous taxon. Find both by comparing row widths with the declared xread size, and fix from the PDF text order (a coding string from the layer missing from the whitespace-stripped markdown points at the break). Short rows that are short in the PDF too are the source's, not ours (Corythosaurus_casuarius 183).

## Extracting a figure image from a PDF: four traps (2026-10-27)

Found while building tree-figure benchmarks from a 200-figure random sample:

- **Caption page is not always the figure page.** PLOS papers can put the caption on one page and the image on the page before; fanti2015a's Fig. 21 caption shares page 36 with Fig. 22's image, while Fig. 21's image is on page 35. Taking "the image on the caption's page" silently gives the wrong figure. Look at what you extracted.
- **White-on-black extractions.** 1-bit image masks (no colour space) and 8-bit Separation (spot-ink) images both come out inverted from `fitz.Pixmap(doc, xref)` + RGB conversion (8% of tree figures). Render the image's page rectangle instead.
- **Flipped or rotated placement.** About 3% of embedded figures are drawn with a flip or 90° matrix (calvo1995a, müller2017z, lerzo2021a, sues2014a); the raw pixels are upside down or mirrored. Check `page.get_image_rects(xref, transform=True)`.
- **Labels outside the raster.** About 5% of figures are a label-free raster with the text set as PDF text on top; only a page render (or the text layer) has the names.
